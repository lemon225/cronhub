## 2026-11-21 · 第四十七批（已上线）· 多步骤链路压测：默认超时 / 重放 / 提取路径 / 传值 · `audit-batch-67`

**起因**：上一批压的是脚本本身（请求体、错误定位、重试语义），这次换成 HTTP 多步骤：用本地 mock 上游按「登录拿 token → 带 token 请求」这种最常见的两段式逐条跑，压出 6 个问题。

**问题与修法**

1. **脚本任务的默认超时其实是 15 秒（P0，注释与行为不符）**
   `runScriptTask` 写着「脚本默认给 60 秒」，但 `sanitizeHttpStep` 无条件写 `timeoutSec: 15`，`|| 60` 永远轮不到。实测一个 18 秒的脚本按默认配置直接被杀，消息「脚本执行超过 15 秒」。
   → `sanitizeHttpStep` 按类型给默认值：脚本 60、HTTP 15（步骤级脚本步骤同理）。前端贴入脚本时若超时还是 15 会自动抬到 60，用户手动改过则不动。

2. **多步骤任务重试会把已成功的步骤重放（P1，副作用）**
   重试是从第一步重跑整个任务。签到成功、领奖 500 的场景，重试一次就是第二次签到 —— 上游多半回「今日已签到」，用户收到的却是失败告警。实测第一步被调用 3 次（配了 2 次重试）。
   → `runHttpSteps` 在失败时若已有步骤成功，给错误打 `sideEffectRisk`；`runTask` 见到就跳过自动重试，并写一条系统日志说明原因。

3. **`extract` 路径不认方括号（P1，静默失效）**
   接口文档给的是 `data.items[0].token`，`pickPath` 只按点号切，取不到值 → 通知退回「HTTP 200」，看着像接口没数据。
   → 先把 `[0]` / `["key"]` 规范化成点号路径再取。

4. **变量值里带引号会把 JSON 请求体打坏（P1，静默坏数据）**
   `{"pw":"{{PWD}}"}`，PWD 为 `a"b` 时发出的是 `{"pw":"a"b"}`，上游只回一句「参数错误」。
   → `applyEnvVars` 新增 `{{json:KEY}}`（值先做 JSON 字符串转义）；请求体声明为 JSON 时，若「原文合法、替换后不合法」直接本地报错并指向 `{{json:KEY}}`，不再发出去。

5. **步骤之间不能传值（P1，功能缺口）**
   「第一步登录拿 token，第二步带着它请求」写不出来，只能退回脚本任务或手抄 token（几小时就过期）。
   → 步骤级 `extract` 落库；每步成功后把提取值注入运行期变量，后续步骤可用 `{{step1.token}}` 或 `{{步骤名.token}}`（中文步骤名也认）。运行期变量只活这一次执行，不写进全局环境变量。
   步骤编辑面板加「提取字段」一行（`token=data.token`，逗号分隔），测试结果里直接显示提取到的值。

6. **单步超时 300 秒，总闸却固定 150 秒（P2，自相矛盾）**
   用户把超时调到 200 秒，任务永远在 150 秒被判「总时长超过」，而那段脚本还在后台继续跑。
   → 总闸改为按任务超时计算：`max(150s, 最长单步 + 30s)`，上限 330 秒（调度锁在这段时间是占着的，再长会撞上 watchdog 的 5 分钟强释放）。

**顺手补的**

- `extract` 的 path/label 加长度上限，任务级与步骤级共用同一套清洗。
- 步骤卡片判空不再只看 url/name：只覆盖请求头、只提取字段的步骤以前会被整张丢掉。
- 请求头里出现中文/全角字符时给可读错误（以前是 Node 的 `Invalid character in header content ["x-token"]`，看不出是哪个变量）。
- 测试接口返回每一步的提取结果，测试面板按等宽小字展示。

**验证**：新增 `tests/http-steps.test.cjs`（16 条断言：默认超时 60/15、方括号路径、两种传值写法、坏 JSON 拦截、`{{json:}}` 转义、重试不重放 + 系统日志说明）；隔离实例端到端 12 项全过（18 秒脚本按默认配置跑完 18372ms、第一步只执行 1 次、中文步骤名传值成功）。`npm test` 18 个用例文件全过。

## 2026-11-21 · 第四十六批（已上线）· 青龙脚本压测二轮：请求体 / 错误定位 / 重试语义 · `audit-batch-66`

**起因**：第四十五批把脚本执行搬进 worker 解决了「卡死」和「逃逸」，但只验证了 `console.log` + `return` 这条最简单的路。这次用真实本地 HTTP 服务，按青龙脚本的常见写法（表单登录、JSON 接口、自定义请求头、错误重试）逐条压，压出 6 个问题。

**问题与修法**

1. **`URLSearchParams` 请求体被序列化成 `{"_l":[[...]]}`（P0，功能不可用）**
   `fetch(url, {method:'POST', body:new URLSearchParams({...})})` 是最常见的登录写法。facade 把 body 原样交给宿主 `JSON.stringify`，上游收到一坨没人认识的 JSON。
   → facade 先归一：`URLSearchParams` 走 `toString()`（`a=1&b=%E5%95%8A`），`Uint8Array`/`ArrayBuffer` 按 UTF-8 解码，字符串原样。

2. **脚本里的 `{{变量}}` 只替换 URL（P1）**
   主进程 `applyEnvVars` 会替换 url / headers / body 三处，脚本侧只在 `doRequest` 里替换了 url。写 `headers: {'X-QW-Api-Key': '{{QWKEY}}'}` 会把字面量发出去，上游回 401，很容易误判成密钥错误。
   → 请求头与请求体也走 `applyEnv`。

3. **脚本报错没有位置（P1）**
   vm 的 message 只有 `Unexpected token '}'` / `boom`，手机上完全看不出死在哪一行。
   → 从 stack 里抽 `script:任务名:行:列`，减掉执行体外层包装那一行后拼进消息：`boom（第 3 行）`；语法错误额外点明「语法错误」。报错点落在 `})()` 上时按代码实际行数收敛。

4. **脚本失败会被当成「可重试失败」（P1，副作用风险）**
   脚本没有状态码，`isTransientFailure` 按「无状态码 = 连接层失败」放行，用户一开重试，签到/领奖脚本就会跑第二遍。
   → `runScriptTask` 失败打 `scriptFailure`，`isTransientFailure` 直接判不可重试；多步骤包装错误时把标记带出去。脚本内部的网络抖动交给脚本自己重试。

5. **空响应 / 非 JSON 只抛 `SyntaxError`（P2）**
   → `res.json()` 对空正文回「响应正文为空，无法解析 JSON（HTTP 200）」，对非 JSON 回「响应不是合法 JSON（HTTP 200）：前 80 字」。

6. **超时与截断的静默行为（P2）**
   - `wait(120000)` 被静默截成 60 秒，脚本以为等了两分钟。→ 超过 60000 毫秒直接拒绝并说明。
   - 输出到 20000 字符直接切断，用户以为脚本只输出了这么多。→ 末尾加 `…[输出超过 20000 字符，已截断]`。
   - 「测试」按钮固定 60 秒上限，300 秒的脚本永远只能看到超时。→ 脚本任务按 `timeoutSec + 20s` 放宽（上限 330 秒），前端请求超时同步放宽。

**顺手补的**

- `Headers` 类：`new Headers({...})`、数组形式、`Headers` 实例传给 `fetch` 都认（青龙脚本常用）。
- 测试面板把脚本输出单列成 `<pre>` 原样展示，不再挤在一行「脚本执行成功，耗时 Xms」里。
- 脚本框支持 Tab 缩进两格（以前 Tab 直接跳焦点，嵌套代码没法排版）。
- 字段提示补一句「脚本任务建议把单次超时调到 30 秒以上」。

**验证**：`npm test` 17 个用例文件全过（脚本断言 26 → 42 条，新增表单体 / Uint8Array / Headers / 头体变量替换 / 错误行号 / 空 JSON / wait 上限 / 截断标记 / 不重试）；隔离实例端到端 4 组：表单体 `u=x&p=1+2` 且头里 `v-777`、失败脚本带「第 3 行」且配 3 次重试仍只跑 1 次（无重试系统日志）、测试接口返回脚本原文、脚本+HTTP 两步均成功。

## 2026-11-21 · 第四十五批（已上线）· 青龙脚本功能加固：线程隔离 / 逃逸面收紧 / 步骤与通知修正 · `audit-batch-64` → `65`

**起因**：前三批把「青龙式脚本任务」做出来了，但只跑通过最简单的一条（`console.log` + `return`）。这次按「能不能交给真脚本用」逐项压测，压出 6 个问题，其中两个是硬伤。

**问题与修法**

1. **脚本能冻死整个服务（P0）**。`vm` 的 `timeout` 只管同步段：`await sleep(10); while(true){}` 之后会进入微任务，`vm` 管不到，`Promise.race` 的超时分支也永远排不上 —— 实测整个进程卡死，调度、HTTP、保活全停，只能等 watchdog 重启。超时之后的脚本还会继续在后台跑（僵尸脚本）。
   → 执行体搬到 `lib/script-runner.cjs`（worker 线程）。主线程到点 `worker.terminate()`，卡死、僵尸、内存爆掉（`resourceLimits` 128MB）全部物理切断。
2. **沙箱可被一句话逃逸（P0）**。之前把宿主内建（`Array` / `Date` / `String` / `JSON` …）注进上下文，`Array.constructor('return process')()` 直接拿到主进程的 `process`；`console.log.constructor(...)` 同理。等于没有任何隔离。
   → 不再注入宿主内建（`vm` 上下文本来就自带完整 JS 内建），宿主能力全部经 facade 包一层：`fetch` / `console` / `sleep` / `setTimeout` / `URL` / `URLSearchParams` / `TextEncoder` / `TextDecoder` / `btoa` / `crypto`。脚本手上只有本 realm 的对象，`x.constructor.constructor` 这条路被 `codeGeneration: false` 挡住。`__host` 桥在 facade 装好后从全局删除，只留在闭包里。
3. **污染主进程全局（P1）**。旧的「切断 constructor 链」写的是 `Object.constructor = undefined`，改的是**主进程**的 `Object`，每跑一次脚本就动一次全局。
   → 随第 2 条一起删除，测试里专门断言跑完脚本后主进程 `Object.constructor` 仍是函数。
4. **多步骤里的脚本步骤被静默丢掉（P1）**。`stepsOf` 的过滤条件只认 `s.url`，脚本步骤没有 url → 整条步骤消失；全丢光时还会退化成「单请求任务」，跑起来跟配置完全不是一回事。
   → 过滤放行 `s.script`；同时规定「任务级 script 只服务单脚本任务」，不再复制到每个 HTTP 步骤上重复执行。
5. **通知无条件报成功（P1）**。`buildRunNotice` 的脚本分支固定回 `✅`，多步骤任务里脚本成功、后面的步骤失败时，手机上看到的是「✅ 成功」。
   → 按整体 `ok` 出 `✅/❌`，并把失败步骤的原因附在正文末尾。
6. **超时根本配不了 / 正文超 FCM 上限（P2）**。前端 `collectForm` 把 `timeoutSec` 写死 15，后端支持的 300 秒形同虚设；脚本输出超过 4096 字节时 FCM 直接 400 拒收（历史实测 1247 字被拒）。
   → 表单加「单次超时（秒）」输入（3–300，默认 15）；透传正文（脚本输出 / `noticeRaw`）加 3600 字节闸，超了才截。
   附带：`safeScriptEnv` 之前把停用中的环境变量也下发给了脚本，现在与 `applyEnvVars` 对齐，只给启用的。
7. **存脚本会被网关 WAF 误伤（P1，线上才发现）**。腾讯 WAF 的 SQL 注入规则把 `sleep(30)` 当攻击特征，保存含 `sleep(数字)` 的脚本直接回一张 403 拦截页（HTML，不是 JSON），前端只报「请求失败 (403)」。批量探针确认触发词就是 `sleep(` 后跟数字：`while (true) {}`、`await 1`、`await fetch(...)` 都放行。
   → 沙箱加同义别名 `wait(ms)`（`sleep` 保留兼容），UI 提示改用 `wait`；前端 `api()` 识别「403 + 非 JSON + 含 WAF」时给出可读原因，不再让用户对着 403 猜。

**验证**：`npm test` 17 个用例文件全过（脚本用例从 8 条扩到 25 条：同步死循环 5 秒截断、await 后死循环 1.5 秒被 terminate、5 组构造器逃逸全阻断、URL/TextEncoder/crypto/subtle/setTimeout 可用、fetch 的 `{{变量}}` 替换与响应头、私网拦截、20KB 输出上限、步骤过滤、env 过滤、通知标题）。本地隔离实例端到端：卡死脚本运行期间 `/api/health` 1.0 秒内正常响应，任务 3.9 秒判失败并带回最后一行日志；多步骤「脚本 + HTTP」两步都执行；配置测试按钮直接跑脚本正常。

## 2026-11-21 · 第四十四批（已上线）· 周报改自然周口径 / 体检补短信中继 · `audit-batch-56` → `63`

**起因**：上一批收尾列出的两条遗留——周报还是「近 7 天滚动窗口」（周一 08:00 发，会把上上周日和本周一各切一刀，和用户脑子里的「上周」对不上）；手动体检扫不到短信中继（中继地址存在 settings 里、不在任务列表，中继挂了体检照样全绿）。

**落地**：

1. **自然周口径**（`weekRangeCN(offsetWeeks, now)`）：东八区周一 00:00 起算。线上容器跑 UTC，直接 `getDay()` 会差 8 小时、周日晚上跑的任务被算进下一周，所以先把时间戳整体 +8h 再按「自 epoch 第几天」取整，最后平移回来——不依赖进程时区，也没有夏令时问题。
2. **`archiveSummary(days, taskId, range)`** 支持绝对区间：range 存在时按 `[fromMs, toMs)` 过滤，返回体额外带 `from`/`to`。原滚动口径（`days`）不变，前端弹窗与主页统计零改动。
3. **`buildWeeklyReport(opts)`** 改为返回对象 `{text, mode, week, from, to, summary}`：默认 `week:'last'` 出上一自然周，`week:'this'` 出本周至今（`to` 截到当前时刻，不把未来算进分母），`week:'rolling'` 保留旧的近 N 天口径。标题随之变成「📊 CronHub 周报 11.09-11.15（自然周）」，结尾措辞按口径说「上周 / 本周 / 近 7 天」。
4. **`GET /api/report/weekly`** 支持 `?week=last|this|rolling`，默认 last；老任务 URL 里带的 `?days=7` 继续有效（rolling 时才生效），无需改任务配置即可切到自然周。
5. **体检补中继**（`runMonitorProbe`）：在「本站」之后固定加 1-2 条中继探针，打 `/__probe`（只读自检，不碰网关、不消耗额度），带 `X-Relay-Secret` 才拿得到上游细节；target 支持自定义 header。中继地址从 `relayEndpoints()` 取，最多两条，多中继时按 host 前缀区分标签。

**验证**：`npm test` 17 个用例文件全过（新增 8 条自然周边界断言：上周一起点、周末＝本周一不含、周日 23:59 不换周、周一 00:00 换周、区间过滤、上周/本周/滚动三种口径互不串味）；线上 `/api/report/weekly` 返回自然周正文（last=11.09-11.15 无记录、this=11.16-11.21 共 24 次全成），`POST /api/monitor/probe` 结果 5 行：本站 / 短信中继 / 三个上游，不再出现重复的本站行。

**踩坑**：

## 2026-11-21 · 第四十三批（已上线）· 对标青龙：随机延迟 / 导入 / 暗黑 / OpenAPI / 脚本任务 · `audit-batch-50` → `56`

**起因**：用户提出「青龙面板很成熟，分析它的功能和特点，优化我们的 CronHub」。调研后确认两者底层模型不同（青龙跑本地脚本，CronHub 调云端 HTTP），只吸收能被 HTTP 模型消化的能力，不移植脚本执行容器与仓库订阅。

**落地（按用户勾选）**：

1. **任务级随机延迟**（`config.randomDelaySec={min,max}` 秒，0-3600）：到点后在区间内随机推迟执行，青龙式防整点风控。只对 cron 节奏生效（interval 会周期漂移），手动「立即执行」不受影响。实现方式是 `computeNextRun()` 把偏移烘焙进 nextRun——不阻塞调度循环、不污染判活（`lastTickAt`）、重启不丢。
2. **配置导入**：数据管理卡加「导入任务」，接受整份导出 JSON 或直接任务数组，按名称匹配覆盖同名、其余新建；只取 tasks 走 `/api/tasks/upsert`，不导入 settings/凭据，带二次确认。
3. **暗黑模式**：顶栏日月按钮切换，`localStorage['cronhub.theme']` 记忆，`<head>` 内联脚本读 `prefers-color-scheme` 防首屏闪烁。CSS 用 `[data-theme="dark"]` 覆盖语义令牌；把散落的硬编码浅底（`background:#fff`/`#fafbfd` 等 40+ 处）收敛到 `--surface`/`--surface-2`，二维码与开关滑块明确保留白色。
4. **只读 Open API**（需单独授权）：`/api/admin/openapi/token` 生成/轮换/关闭，只存 SHA256、明文只显示一次；`/api/open/{tasks,state,health,archive}` 只读、仅 GET、每 token 每分钟限 60 次；`settings` PUT 忽略 back 来的 openApi 字段防绕过。
5. **脚本任务**（青龙式，主进程内跑 JS）：http 任务配 `config.script` 即在 node:vm 白名单沙箱执行，暴露 `fetch/console/env/sleep`，不提供 `require/process`、切断 constructor 逃逸、vm timeout + 总 deadline + 输出上限；脚本输出直接作为通知正文。定位是「自己写的可信脚本」，UI 与文档均标注不可信脚本勿运行。

**踩坑与修复**：

- Open API token 最初用 Bearer header，线上始终 401。诊断发现 **WorkBuddy 托管网关会往 `authorization`/`x-open-token` 注入它自己的 ~379 字认证串**，抢占了自定义 token。修复：`?token=` query 优先（与 `?sharecode=` 同通道可透传），并给异常长度候选直接判无效。前端文案同步改成 URL 参数传。

- 脚本任务首版通知正文退化成「HTTP 200，耗时 xx ms」：脚本输出是纯文本、`heuristicFacts` 只解析 JSON。给步骤结果加 `scriptOutput` 标记，通知层据此用脚本输出作正文。
- 无密码访问模式下 token 管理端点原要求 admin 会 403：改为「没开密码 = 单用户可信，放行；开了密码才要 admin」。

**验证**：`npm test` 17 个用例文件全过；`/api/health` build 56、`warnings=[]`；真实浏览器截图核对暗黑模式（含归档卡/监控格）与编辑面板脚本字段；线上实测 OpenAPI 三种鉴权场景、脚本任务端到端输出、周报/任务数未受影响（13 个任务）。

**明确未做**：仓库订阅自动拉取、Python/Shell 脚本执行（云端缺运行时且有 RCE 风险，项目已有独立 `cloudfn/` Worker 承接）。

**现象**：天气播报任务连续 3 次失败，报「[实况] 失败：请求失败：响应未读完连接已关闭」。
同一时间用 curl 直连同一个 URL 是正常的，任务配置、密钥、网络都没变。

**根因**（第十六批引入的回归）：`readBody()` 把底层 `res` 的 `close` 一律当成断连。
但解压是异步的 —— 报文收完、连接归还池子的那一刻，`gunzip` 还差一个 tick 才吐出最后一块，
`close` 就抢在解压流 `end` 之前把 Promise 判死了。于是**上游只要真的返回 gzip，任务就 100% 失败**，
而且真实状态码被这条假故障完全盖住（和风天气走 CDN，即使请求没带 `accept-encoding` 也无条件压缩）。
实测该 URL 连续 4 次全部复现，本地自建 gzip 响应亦然。

**修复**：
- `close` 时先看 `res.complete`：报文完整就再给解压 3 秒宽限（超时才判失败，防止解压流卡死把 Promise 挂住 → ticking 锁死）；只有 `complete === false` 才是真断连
- `aborted` 事件同样按 `complete` 过滤，避免与 `close` 重复判死
- 附带效果：401 / 432 这类错误响应现在能把状态码和正文如实报出来，不再被伪装成网络故障

**验证**：
- 新增 `tests/http-client.test.cjs`（13 项）：gzip 200 能解压、gzip 401 能拿到状态码与正文、deflate/brotli 都能解、

**主题**：把「系统随时可能归零」和「跑着跑着数据没了」这两件事堵掉，并让「错过的任务」既补得上、又不重复跑。

### ① 数据不丢（最关键）
原实现是「写 tmp → rename」，且解析失败只 `console.error` 然后起空状态，第一次写盘就把坏文件覆盖掉 —— JSON 只要坏一次，8 个任务、200 条通知、凭据保险库全部消失，事后连取证机会都没有。

- 写盘改成 `open → write → fsync → close → rename` 四步，tmp+rename 只保证目录项原子，不保证数据页落盘
- 三级备份轮转 `state.bak.1/.2/.3`（默认 12 分钟一份，`STATE_BAK_INTERVAL_MS` 可调）
- 解析失败：先把坏文件改名隔离成 `state.corrupt.<时间戳>`，再从最近一份可解析的备份恢复，并推手机告警；**绝不静默清零**
- `/api/health` 新增 `storage` 快照：fsync 是否生效、备份时间、本次加载来源、是否发生过损坏回退
- 验证：`tests/state-durability.test.cjs` 20/20（截断、清空、全坏三种故障注入）

### ② 进程不倒
- `tickWatchdog`：调度锁被占超过 5 分钟强制释放并告警（此前一个任务卡死 = 调度永久停摆，界面只表现为「任务不跑了」）
- `runTaskGuarded`：单任务总时长上限 150 秒，超时放行调度而不是拖死整轮
- `uncaughtException` 记日志后走受控退出，交给守护重启（原实现捕获后继续跑，状态已不可信）
- `SIGTERM` 给 5 秒 grace 等在途任务收尾，不再硬切
- 新增 `watchdog.cjs`：子进程守护 + 崩溃自愈 + 重启计数（`npm run start:guard`）
- 验证：`tests/watchdog.test.cjs` 全部通过（强杀后自动拉起、新 PID 不同、state.json 仍可解析）

### ③ 错过补跑（可控）—— 本次重点
原来只有 `missedPolicy=run|skip` 两态，且 `run` 是「唤醒后立刻跑」：8 个任务同一秒打向同一个上游，既可能重复执行（那次其实已经跑过，只是没落下 nextRun），又正好是服务方风控最敏感的特征。

现在改成「补，但克制」：

| 判据 | 行为 |
|---|---|
| 错过 ≤ 窗口（默认 120 分钟） | 补 |
| 超过窗口 | 不补，只推进排期 + 通知说明 |
| `lastRun` ≥ 错过时刻 | 不补（那次之后已经跑过，绝不重复） |
| 距上次执行 < 最小间隔（周期 55%，上限 45s） | 不补（防「补跑 + 准点」连打上游） |
| 任务级 `config.noCatchup` | 不补（下单、抽奖类） |
| 单次启动超过上限（默认 5 个） | 丢弃并说明，不做启动风暴 |

- **错过 5 次也只补 1 次**，不补齐历史（补跑不是追债）
- **认领先落盘**：启动时就把 nextRun 推进到未来并写盘，补跑中途被回收也不会再来一次
- **串行 + 随机抖动**（默认 20 秒上限）：同一时刻只有一条请求出去；补跑期间 tick 主动让路
- **补跑后冷静期**：若下一次计划紧贴（< 最小间隔），顺延一次，只错开不改长期节奏
- 设置页可调：开关 / 窗口 / 单次上限 / 最小间隔 / 抖动上限（改完即存，服务端逐项夹紧）
- 任务编辑新增「服务中断后不自动补跑」开关（默认关 = 允许补跑）
- `/api/health` 与 `/api/state` 的 `catchup` 快照：计划几个、补成几个、跳过几个及原因
- 验证：`tests/catchup.test.cjs` 23/23（五类判定的正向与反向都验，含重启幂等与单次上限）

### ④ 工程基建
- `git init` + 基线提交：此前 8600 行核心代码零版本控制，改坏无法回滚
- 测试从 `D:\Temp` 搬进项目 `tests/`，`npm test` 一键跑（3 个用例文件、54 项断言）

## 2026-11-12 · 第十五批 · `audit-batch-15` · 网站 ↔ Cloudflare 联通加固

**主题**：把「网站」和「Cloudflare 中继」之间这条路修好 —— 降延迟、加冗余、让慢的地方看得见。
优化前先测了一遍基线（本地直连中继）：首次请求 1927ms，其中 TCP 519ms + TLS 233ms，
即**每次握手约占 40%**；复用连接后 468ms。

### ① 降延迟：连接复用 + 启动预热

| 改动 | 为什么 |
|---|---|
| `probeSmsRelay` / `guardSmsRelay` 从全局 `fetch`（undici，keepAlive 只有 4s）切到 `lib/http-client.cjs`（keepAlive 60s + DNS 缓存 + TLS 会话复用） | 探针与体检之间只要间隔超过 4s，undici 就扔掉连接，下次又从 DNS + 三次握手 + TLS 重来 |
| 新增 `warmRelay()`：启动 3 秒后预热一次，结果记进 `companion.warm` | 设置页点「自检」、唤醒即陪护这类**交互触发的第一次请求**不用再等握手（线上实测预热 3145ms 一次付清，之后每次 490~1059ms 且 `reused=true`） |
| `lib/sms/send.cjs` 中继模式改用进程内 keepAlive Agent | 同一子进程内的重试 / 换域名 / 换中继都复用握手：实测第一次 1821ms（新建，握手 458ms），第二次 **547ms（复用，握手 0ms）** |

> 说明：真正发短信是短命子进程，本站进程的连接池帮不到它，两条链路各自优化、不混谈。

### ② 加可靠性：主 + 备地址、故障转移、连续失败告警

- `settings.smsGatewayRelay` 新增 `urls`（备用地址数组），`url` 仍是主地址；保存时统一去重、
  **只留 https origin**（明文地址会让短信令牌在公网裸奔），一条坏配置不会废掉整条链路。
- `relayEndpoints()` 是唯一的地址解析入口：发送、探活、体检、`companion` 全走它。
- **发送端故障转移**：`send.cjs` 按顺序试各条中继，传输层失败（连不上 / 5xx / 超时 / DNS 失败）
  立刻换下一条，不等整轮重试。实测「主地址 ENOTFOUND → 立刻切备用成功」。
- **重试粘性**：记住上次真正把请求送到对端的那条中继，下一轮重试优先走它。
  以前每轮都从主地址开始，主地址挂了 3 轮就是 3 次 ENOTFOUND，白等几秒。
- **探活并行**：所有中继同时探，`relay.upCount` 给出「几条通」，最快的标为「当前使用」。
- **连续失败告警**：`guardSmsRelay` 连续失败第 2 次起推 NotifyMe（1 小时内不重复），
  **绝不回落到短信** —— 短信正是那个挂掉的通道。

### ③ 让慢的地方看得见：分段耗时

- `lib/http-client.cjs` 支持可选 `timing` 采集：`reused / connectMs / tlsMs / ttfbMs / totalMs`。
- `send.cjs` 每次发送打一行 `[relay-timing] {...}`，服务端解析后并入 `relayHealth.timing`，
  **再从用户可见的发送结果里剔掉**（诊断信息不进日志正文）。
- 判定「是否复用」只看「这次请求期间有没有真的发生 connect 事件」。**不能用 `socket.connecting`**：
  TLS socket 上这个属性不可靠，新建的 https 连接也会读成 `false`，会把每次新建都标成「复用」——
  诊断结论直接反过来（这个坑是实测踩到的）。

## 2026-11-11 · 第十四批 · `audit-batch-14` · 全量代码审阅后的可靠性加固

- `lib/http-client.cjs` 的 `readBody()` 改成**无条件**监听底层 `res` 的 `aborted / error / close`。

## 2026-11-11 · 第十二批 · `audit-batch-12` · 提示词分层 + 机器校验 + 前后对比

**主题**：第十一批上线后任务要求确实进了 system（线上 `aiNote` 已显示「按任务要求」），
但用户仍觉得「要求不生效、优化效果不明显」。用线上同一套模型做了 A/B 对照实验，
发现真正的问题不是「没照做」，而是「照做了也对不上」：

| 实验现象 | 根因 | 修法 |
|---|---|---|
| 同一输入两次输出，油价 5 行 / 4 行，云音乐 1 行 / 6 行 | 温度 0.6 + 没有结构契约，每次排版重新摇骰子 | 温度降到 0.35；提示词加「第一行给结论」等体例约束 |
| 把「92 号 8.89 元/升」写成「92号：8.89升」 | 只写了「不得编造」，没要求保留单位 | 事实纪律单列「数字必须带原单位」，并把丢单位写成反例 |
| 热评通知被加一句「建议理性看待竞技结果」 | 默认要求里「如有必要…提出生活建议」被当成必答项 | 禁止空话清单 + 「建议必须是数据推得出来的具体动作」 |
| 任务要求写到 1413 字就吃满上限 | 保存时硬截 1500 字，尾部（往往正是排版细则）被静默丢弃 | 上限 1500→4000，全局默认 500→2000，前端显示字数并在超限时标红 |
| 写了「每行 ≤24 字」但没人检查 | 规则只写在提示词里，生成后没有任何验证 | 从要求里抽可机检条款，生成后逐条检查，不达标自动纠正一次 |

**提示词结构**（`aiPrompts()`，与预览接口共用同一份，不另写副本）：
先判材料类型（结构化数据 / 长文本）→ 事实纪律 → 禁止的写法 → 体例 → 本任务要求。
任务要求只压「体例」，**压不动事实纪律与禁写底线**；默认要求退到 user 当补充。
长文本明确要求「提炼 2~4 个要点，禁止逐句照抄」—— 之前两类材料共用一套指令，热评类会退化成照抄原文。

**机器校验**（`aiRules()` / `aiReview()`）：抽取 `每行 ≤N 字`、`正文 ≤N 字`、
`每行 1 个 emoji`，加三条通用底线（禁 markdown / 禁空行 / 禁空话）。硬规则不达标
时把「具体违反了哪一条」回灌模型纠正一次；两次调用是上限（默认 attempts=2），
纠正后仍不达标就照发，但 `aiNote` 如实写「M 项未达标：第 2 行 27 字…」。
字数按**去空白**计 —— 按含空白算会把合规输出（每行 17/23/18 字）误判成超长。

**新增可见性**：
- 任务编辑 AI 区加「看实际提示词」：直接展示真实发出去的 system / user + 抽出的校验条款。
- 通知卡片加「看 AI 前的原文」：`rawBody` 落地，一键对比 AI 改了什么。
- `aiNote` 从「按任务要求」升级为「按任务要求，已校验 5 项」/「2 项未达标：…」，可核对而非自我声明。
- 设置页那句「总提示语 = 开头 + 任务要求」已过时，改成「补充要求，优先级低于任务要求」。

**实测**（线上模型 agnes-3.0-flash，真实接口数据）：
油价播报单位保留、区分「现价/预计」、无空话；热评从照抄改为摘要；写死三行排版的任务一次成型。

# 提示词全景

> 读者是模型，不是人：每条要么指向一个字段，要么指向一个输出位置；不写理由，不写版本戳。
> 对应代码：`server.js` 的 `aiPrompts()` / `aiRules()` / `aiReview()` / `orderBandAfterDay()`。
> 最近整理：2026-11-15 第三十批（`build=audit-batch-31`）。

## 写入原则

1. **声明式**：写「〈降水=〉＝取同名字段的值」「缺最高 → 只写最低」，不写「宁可缺一项，不可编一项」这类修辞——模型不缺态度，缺的是字段映射。
2. **映射只写一遍**：字段名直接嵌进模板占位符（`〈降水=〉`），不再另列一张「现象←… 最低←…」对照表。两套名称＝两次翻译，迟早对不上。
3. **先给形态，再给规则**：模板放在引用它的规则之前。「第 3 行＝…」写在模板之前会悬空，实测直接丢掉预警与降水时段。
4. **能查表就别写散文**：建议句与图标合成一张 `条件 → 图标+短句` 的对照表，模型不用做两次独立决策。
5. **能数就别形容**：`3 行`、`58 字`、`≤160 字`，都不留给模型自己判断。
6. **元信息不进提示词**：版本号、编辑时间、地点、日期放本文件或数据区；`{{日期}}` 这类没人替换的占位符只会被模型当文本读，已删。
7. **机检触发词是字面量**：删掉那句话＝关掉那条校验，见第 5 节。

## 拼装顺序

```
system = 内置骨架（579 字）+ 【本任务要求】（任务 config.notifyPrompt，可空）
user   = 任务 / 【原通知】或【材料】/【接口原始数据】/【默认要求】/【自检】
```

优先级：**任务要求 > 体例 > 默认要求**；**事实、禁止 > 任务要求**。

`【原通知】` 与 `【材料】` 二选一：有 `rawData` 时原文只是「可参考、非事实来源」；没有 `rawData` 的长文本任务（热评）里，原文就是材料本身。混用会让模型把上一版通知当数据抄。

## 1 内置骨架（579 字，随代码走）

| 段落 | 管什么 | 下游机检 |
| --- | --- | --- |
| 角色与输出契约 | 只输出 `{"title","body"}`；body 内 `\n` 分行 | 解析失败即重试 |
| 事实｜不可违反 | 数字/时刻/名称逐字可查；带原单位；多口径不合并；缺项不占位 | `fact-number` |
| 按材料形态选写法 | 结构化数据只留 3~6 项；长文本提炼 2~4 点 | — |
| 禁止 | 空话与泛建议（合并成一条）、字段名入正文、自称 | `no-filler` |
| 体例｜**默认值：任务要求可逐条覆盖** | ≤160 字、首行给结论、中文标点、数字与单位留空格 | `no-markdown` `no-blank-line` |

`体例` 是「默认值」不是「硬规定」：天气任务要求 `°C` 紧贴数字，与骨架的「留空格」正面冲突，由提示词先声明覆盖关系，代码侧 `tightUnits` 只是兜底。

## 2 全局默认提示词（25 字）

```
精简易读，突出关键数字；必要时给一句具体建议。
```

10 个没有自定义提示词的任务共用。**别写成含「每行 N 字」「只输出 N 行」的句子**——那会给所有任务凭空加一条机检。

## 3 天气任务提示词（813 字）

任务 `task_2c265324420b`「天气预报·三甲集」，正本 `docs/notifyPrompt-weather.txt`。

```
天气播报改写器：把【事实结论】的字段填进模板，不改写、不推算。

【数据源】只取【事实结论】里模板点名的字段；逐日/逐小时行、状态串、【原通知】只供核对，不作数据；字段缺失→删该字段。

【模板】〈字段=〉取同名字段的值，〈〉是占位符，不照抄、不当事实
❄️ 今晚〈降水=〉〈现象=〉，最低〈最低=〉°C
⛅ 明天〈降水=〉〈现象=〉，〈最低=〉~〈最高=〉°C
〈预警名=「无」→ 建议；否则 → 预警〉
· 「今晚」「明天」写全、留在行首；信息点用「，」；只输出 3 行。
· 正文 ≤58 字；超限按序删：建议短句 > 明天温度区间 > 今晚最低。现象/降水/预警不删。
· 缺最高只写〈最低=〉°C；缺最低删整段温度；行末不加句号。

【降水】紧跟日期词、作现象的定语：今晚19-07时小雪。
· 已是 24 小时制区间，末尾一个「时」；不加「起/停/到/至」，不拆成两个「N时」、不单独成句、不与温度换位。
· 两行独立：一行有值不得省另一行、不得互换；正文每个「N时」须在结论区降水区间内。

【第 3 行】有预警 → ⚠️ 〈预警名〉；明早慢行。逐字照抄，不加级别词、不减字；⚠️ 全篇只出现一次。
无预警 → 按第一个命中取，图标与短句成对：
结冰/降雪/低温 → 🧣 明早慢行　降雨 → ☔ 带伞　沙尘/雾霾 → 😷 戴口罩　晴热 → 🧢 防晒
其余 → 💡 一句数据相关的具体建议

【图标】今晚行/明天行按现象选，全篇不重复：
晴☀️ 多云⛅ 阴☁️ 雨🌧️ 雨夹雪｜雪❄️ 雾🌫️ 雷⛈️ 沙尘🌪️ 风≥5🌬️ 夜间晴🌙
表内天气词是选图标识，不是本次事实。

【单位】°C 紧贴数字，每个温度只带一个 °C；~ 两侧不留空格。

【降级】结论区为空或两行都取不到字段 → 只输出：
❄️ 数据不足
⛅ 本次不播报
💡 稍后重试

【裁决】禁止编造 > 数据源 > 模板 > 字数。
```

### 每段为什么这么写

| 段 | 作用 | 踩过的坑 |
| --- | --- | --- |
| 模板 | 交付形态前置，占位符自己带字段名 | 模板排到规则之后 → 预警、时段双双丢失；另列一张映射表 → 两套名称互相打架 |
| 数据源 | 只声明「哪儿不许取」，映射交给模板 | 只写「只能取自结论区」时，模型会自己去逐小时行里找时段 |
| 降水 | 「时段是定语」＋位置示例，把时段钉在现象前 | 模型会把时段写成独立信息点：「今晚小雪，19-07时」 |
| 预警 / 建议 | 合并成【第 3 行】一节，有预警走预警、无预警按条件取建议 | 分成两节时两条「第 3 行」谁优先得靠模型猜；按级别换行要挤第 4 行，实测会把预警整行丢掉 |
| 图标 | 只做选图，声明「表内天气词不是事实」 | 否则把「雨夹雪」当成本次现象写进正文 |
| 单位 | 显式声明覆盖「体例」的留空格 | 冲突未裁决时输出会在 `-1.4°C` / `-1.4 °C` 之间摇 |
| 裁决 | 末行给优先级，利用末位权重 | 冲突没有裁决顺序时，模型随机选一条遵守 |

### 删掉的

`编辑时间` 版本戳、`地点`＋`今天 {{日期}}`（envVars 为空，占位符原样进模型）、字段映射对照表（并入模板）、`只输出 3 行`之外的行号前缀（`行1　`，会被当正文抄）、`禁 markdown / 空行`、`行末不加句号` 的重复表述、按级别换预警行的分支、风级/紫外线/湿度阈值表。

## 5 机检规则触发词（改提示词别删这些字）

| 规则 | 触发条件 | 硬/软 | 删了会怎样 |
| --- | --- | --- | --- |
| `line-count` | 出现「只输出 3 行」 | 硬 | 少写一行照发 |
| `total-max` | 出现「正文 ≤58 字」 | 硬 | 超长不拦 |
| `unique-icon` | 出现「全篇不重复」 | 软 | 三行同图标，`dedupeIcons` 也不启用 |
| `fact-source` / `fact-band` | 出现「事实结论」 | 硬 | 编造的现象词、时段全部放行 |
| `tightUnits` | 同时出现「紧贴」与「°C」 | — | `°C`、`~` 的归一不执行 |
| `line-max` | 「每行 ≤N 字」 | 硬 | 天气任务不用它，别误加 |
| `emoji-per-line` | 「每行 1 个 emoji」 | 软 | 天气任务不用它，别误加 |

## 6 确定性归一（代码侧兜底）

模型即使 `temperature=0` 也会抖，凡是「改一下就能读通」的排版偏差都交给代码，不再多花一次调用：

| 函数/开关 | 处理 |
| --- | --- |
| `tightUnits` | `-1.4 °C` → `-1.4°C`；`-1.5 ~ 6°C` → `-1.5~6°C` |
| `dedupeIcons` | 重复图标按池顺序换成未用过的（`unique-icon` 才启用） |
| `orderBandAfterDay` | ①`19-07时今晚小雪` → `今晚19-07时小雪`；②`今晚小雪，19-07时` → 并回现象前；③`⚠️ …，明早慢行` → 分号 |
| `AI_POLISH_CACHE` | 按事实结论指纹缓存 30min，同材料同输出 |

## 8 改动入口

- 全局默认：`PUT /api/settings`，body 只带 `{"ai":{"defaultPrompt":"…"}}`；服务端对掩码 `apiKey` 有保留逻辑
- 任务提示词：`POST /api/tasks/upsert`，`items` 里放**完整 task**（只带 `config.notifyPrompt` 会丢 url/steps）
- 改完必查：`\uFFFD` 为 0、长度与源文件逐字一致、`steps` 与 `retry` 未变
- 不调模型的验证：`POST /api/ai/preview`（回 `system` / `user` / `rules`）

## 9 数据侧：明天夜间有雨雪却没承载行（三十二批）

`qWeatherFacts()` 的明天行原本只取 `days[1].daytime`（07-19 时）。今晚行覆盖今晚 19 点到明天 7 点，明天行覆盖明天 7-19 点 —— 明天 19 点到后天 7 点这一段没有任何一行承载。冬天「白天多云、夜里下雪」正是最常见的一种，通知却写成「明天多云」。

| 位置 | 现在的做法 |
| --- | --- |
| 取哪一段 | 明天行先取白天；白天没降水而 `days[1].nighttime` 有，就退回夜间 |
| 现象 | 跟着换成夜间那条，「降水」和「现象」必须出自同一段 |
| 温度 | 仍取全天极值（`days[1]` 的最低/最高）；夜间只有最低，混着取会把区间砍成半个 |
| 降水区间 | 两行并集去重，两段同为 `19-07时` 时只写一次 |

会拼出「明天19-07时中雪」——按 24 小时制读是明天 19 点到后天 7 点，和今晚行靠「今晚 / 明天」区分，不算歧义。用例 `tests/weather-ai.test.cjs` 的「白天没降水时，明天行退回明天夜间」守住这条。
